Touched file only: public/sitevento.js — DEBUG BUILD

WHAT THIS BUILD DOES DIFFERENTLY
  1. API_ORIGIN is hardcoded to 'https://sitevento12.vercel.app' instead
     of being derived from currentScript.src. This rules out — or
     confirms — whether the origin-detection logic was ever the actual
     problem (e.g. document.currentScript being null, a proxy rewriting
     the script's own src, etc). It also logs what the normal detection
     WOULD have resolved to, for comparison, right next to the
     hardcoded value.

  2. beacon() no longer tries navigator.sendBeacon() first. It always
     uses fetch() with a real .then()/.catch(), and logs:
       - every outgoing beacon URL + payload
       - the HTTP status code of the response
       - the response body (useful since /api/track returns JSON like
         {ok:false, reason:'unknown site'} on an expected failure)
       - any network/CORS failure, with the actual error object

HOW TO USE IT
  1. Replace your current public/sitevento.js with this file and deploy.
  2. Open the live customer site (e.g. testhoyoo.oneapp.dev) in a
     browser, open DevTools -> Console, and reload the page.
  3. Look for lines starting with [sitevento]. You should see, in order:
       [sitevento] debug build active. siteId = ... API_ORIGIN = ...
       [sitevento] (for comparison) currentScript.src = ...
       [sitevento] sending beacon -> https://sitevento12.vercel.app/api/track {...}
       [sitevento] beacon response: 200 https://sitevento12.vercel.app/api/track
     (or an error instead of that last line if it's blocked/failing)

WHAT EACH OUTCOME TELLS YOU
  - No "[sitevento] debug build active" line at all
      -> the script never loaded/ran. This confirms the 404 (or
         whatever is preventing the <script> tag from executing) is
         still the root blocker — nothing past this point can run.
  - "debug build active" appears, but no "sending beacon" line follows
      -> the script loaded but returned early. Check for the
         "no data-site attribute" error just above it.
  - "sending beacon" appears, then a BLOCKED/FAILED error
      -> network/CORS/DNS issue reaching API_ORIGIN itself (wrong
         domain, site down, CORS headers misconfigured on the route).
  - "sending beacon" appears, then "beacon response: 200" with a body
    like {"ok":false,"reason":"unknown site"} or
    {"ok":false,"reason":"site not verified"}
      -> the request IS reaching /api/track successfully. The remaining
         issue is in Firestore lookup logic (siteIndex doc missing,
         status not actually 'verified', etc), not in the script or
         network layer at all.
  - "beacon response: 200" with {"ok":true}
      -> tracking is fully working end-to-end. Check the dashboard's
         onSnapshot listener next if stats still don't show there.
